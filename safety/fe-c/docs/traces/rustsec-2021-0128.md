# Worked trace: RUSTSEC-2021-0128 (`rusqlite` closure lifetime → stack UAF across FFI)

Status: **design validation + spec for integration test `corpus/rusqlite-0128`.**
Companion to `docs/traces/rustsec-2021-0130.md`. Chosen because it is the
cross-language case: the free is a *Rust stack frame teardown*, the dangling
access happens inside a **callback invoked by C**, and neither the lru trace
nor SafeFFI's published design fully covers that path.

## The bug

`rusqlite` registers Rust closures with SQLite (C) to be invoked later:
`create_scalar_function`, `create_aggregate_function`, `create_window_function`
(feature `functions`); `commit_hook`, `rollback_hook`, `update_hook`
(`hooks`); `create_collation` (`collation`). The lifetime bound on these
closure parameters was too relaxed: a closure capturing borrows of **stack**
values could be registered, outlive the frame those borrows point into, and
then be invoked by SQLite — reading dropped stack objects.

Affected: 0.25.0–0.25.3, 0.26.0–0.26.1. Fixed in 0.25.4 / 0.26.2.
Advisory RUSTSEC-2021-0128 (CVE-2021-45713…45719).

Shape of the reproducer:

```rust
let db = Connection::open_in_memory()?;
{
    let local = String::from("dropped when this block ends");
    // pre-0.25.4: accepted despite `local` not outliving `db`
    db.create_scalar_function("f", 0, flags, move |_ctx| {
        Ok(local.len() as i64)          // reads `local` when SQLite calls back
    })?;
}                                        // `local` dropped here
db.query_row("SELECT f()", [], |r| r.get::<_, i64>(0))?;   // C invokes the closure
```

The closure box is passed to `sqlite3_create_function_v2` as a `void*`
`pApp`; SQLite stores it, and later calls a Rust `extern "C"` trampoline with
that pointer. Nothing on the Rust side is looking at the borrow anymore.

## Trace under `--harden=case`

| # | Program event | Fe-C action | Table |
| - | ------------- | ----------- | ----- |
| 1 | `local` created on the stack; closure boxed with a borrow of it | boxed closure registered by the allocator; the *captured borrow* points into the current stack frame | `id=B` (closure box) live; frame region registered at frame entry |
| 2 | `create_scalar_function` passes the box as `*mut c_void` into C | **outbound FFI**: pointer leaves Rust; provenance recorded as escaped-to-foreign | `id=B` marked escaped |
| 3 | Block ends: `local` dropped, frame region for that scope torn down | **frame teardown deregisters the scope's stack region** (epoch bump, poisoned until re-entered) | stack capability covering `local` now dead |
| 4 | SQLite calls the Rust `extern "C"` trampoline with `pApp` | **§3.3 FFI prologue check**: `ensure_foreign_arg(pApp, size_of::<Box<F>>())` — the box is still live, so this **passes** (correct) | `id=B` live |
| 5 | Trampoline reborrows the closure and the closure reads `local` | **§3.2 pointer-loaded-from-memory check** on the captured reference, then the access | captured pointer resolves into the **dead** stack capability → **abort** |

Under `--harden=through`, step 5 traps at the access itself with no reliance on
the load-site check.

## Findings

### F5 — stack frames must be table-registered, not just heap allocations

The lru trace only exercised heap capabilities. Here the freed object is a
**stack** local. If the table only knows about `malloc`/`Box` allocations,
step 5 resolves the captured pointer to *no capability* and, under the v0
default `permissive` unknown-provenance policy, would **degrade to a null/
alignment check and pass** — a false negative on a real CVE.

Consequences for the plan:

- `cementite` must register **stack scope regions** (frame or lexical-scope
  granularity) with their own ids/epochs, torn down on exit. The MIR pass
  emits scope enter/exit hooks; cost is per-scope, not per-access.
- The unknown-provenance policy needs a third setting beyond
  `strict`/`permissive`: **`strict-stack`** — unknown heap provenance is
  tolerated (foreign statics like `getenv` are legitimate), but a pointer that
  resolves *into a known-but-dead stack region* is always fatal.
  This should be the v0 default; it is strictly more precise than `permissive`
  and does not inherit `strict`'s false-positive risk on foreign statics.
- Frame-teardown poisoning is what makes stack use-after-return detectable at
  all — it is the same mechanism §3.3's `ensure_returned` depends on, so the
  two checks share one implementation.

### F6 — outbound FFI needs escape recording, not just inbound checking

The plan's §3.3 covered pointers *arriving* from foreign code. This CVE runs
the other direction first: Rust hands a pointer **out** to C, C stores it, and
the danger materializes on the way back. Two additions:

- Record escape at outbound `extern "C"` call sites (pointer args become
  `escaped`). Escaped allocations must be **exempt from any elision** that
  assumes Rust-exclusive access, and are candidates for quarantine-on-free
  even in otherwise-fast crates.
- Escaped-allocation liveness is what makes step 4's prologue check meaningful:
  without it, a genuinely freed closure box arriving from C would look like an
  ordinary unknown pointer.

### F7 — `case` mode catches this, but the honest framing is "detects", not "prevents"

The abort happens *inside the callback*, after C has already re-entered Rust.
Nothing was corrupted, so detection is timely — but the report must name the
**registration site** (`create_scalar_function`) rather than only the callback,
or the developer sees a stack trace through SQLite's internals with no link to
the actual mistake. Extend `Violation` with an `escaped_at: Option<SiteId>` so
outbound-escape provenance survives into the report.

### F8 — this bug is a *lifetime* bug, and that is the boundary of the tool

The root cause is a too-relaxed lifetime bound — a **type-level** error that
`cargo audit`, Yuga-style static analysis, or a fixed signature prevents
outright. Fe-C converts it from silent UB into a deterministic abort; it does
not prevent it. Worth stating in the README threat model beside the F3
concurrency caveat: Fe-C is a *detection and containment-of-consequences*
tool for exactly this class, not a substitute for correct lifetimes.

## Integration test spec (`corpus/rusqlite-0128`)

- **Fixture**: vendored `rusqlite` 0.25.3 (pinned) + bundled `libsqlite3-sys`.
  Note this is the first corpus entry that pulls **real C** — it doubles as the
  mixed-language build smoke test for the whole toolchain.
- **Assert (case)**: process aborts inside the callback; report names the dead
  stack scope, the callback site, **and** (per F7) the registration site.
- **Assert (through)**: aborts at the access.
- **Assert (control)**: same program against 0.25.4 runs clean in both modes.
- **Assert (C-side sanity)**: the SQLite C code itself is *not* instrumented in
  this configuration; the test documents that only the boundary is checked —
  the F8/threat-model point, made executable.
- Runs as a `nix flake check`; `libsqlite3-sys` vendored so the check stays
  pure/offline.

## Plan deltas produced by this trace

1. New invariant **I8**: stack scope regions are table-registered with
   enter/exit hooks (F5).
2. New invariant **I9**: outbound FFI records escape; escaped allocations are
   elision-exempt and quarantine-eligible (F6).
3. §3.3 grows an outbound half; unknown-provenance default becomes
   `strict-stack`.
4. `Violation` gains `escaped_at` (F7).
5. README threat model gains the "detects, does not prevent, lifetime bugs"
   line (F8).
