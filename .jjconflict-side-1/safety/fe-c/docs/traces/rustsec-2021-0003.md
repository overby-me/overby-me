# Worked trace: RUSTSEC-2021-0003 (`smallvec::insert_many` heap overflow)

Status: **design correction + spec for integration test `corpus/smallvec-0003`.**
Third trace, after `-0130` (temporal, heap) and `-0128` (temporal, stack, FFI).
This one is spatial — and it breaks the design as written **twice**.

## The bug

`SmallVec::insert_many` reserved space using the iterator's `size_hint()`
*lower* bound, then wrote every item the iterator actually yielded. An iterator
whose lower bound understates its length (e.g. any `filter`) overflows the
buffer. Affected < 0.6.14 / < 1.6.1; found by Rudra (SSLab, Georgia Tech).

Reproducer (upstream servo/rust-smallvec#252) — note the attribute:

```rust
#![forbid(unsafe_code)]
use smallvec::SmallVec;

fn main() {
    let mut v: SmallVec<[u8; 0]> = SmallVec::new();
    v.push(123);                               // spill to heap
    let s = String::from("Hello!");            // neighbouring heap allocation
    let iter = (0u8..=255).filter(|n| n % 2 == 0);
    assert_eq!(iter.size_hint().0, 0);         // lower bound lies
    v.insert_many(0, iter);                    // reserves 0, writes 128
    assert!(v.as_ptr_range().contains(&s.as_ptr()));  // s is now inside v
    println!("{}", s);                         // corrupted
}
```

Two properties make this the interesting case:

- The caller is 100% safe Rust (`forbid(unsafe_code)`). The unsafe is entirely
  in the dependency — the archetype of "the bug is yours only in the sense
  that you depend on it."
- The overflow lands **inside another live allocation** (the `String`). There
  is no unmapped page, no guard region, no segfault. The address written is
  perfectly valid; it just doesn't belong to `v`.

## Trace under `--harden=case`

The write path is raw: `self.as_mut_ptr()` → `ptr.add(index)` → `ptr::copy` /
`ptr::write`, all inside `unsafe` in smallvec.

| # | Program event | Fe-C action |
| - | ------------- | ----------- |
| 1 | `v.push` spills → heap alloc of 1 byte | allocator registers `id=V (base_v, len=1, epoch=1)` |
| 2 | `String::from` allocates | registers `id=S (base_s, len=6, epoch=1)` |
| 3 | `insert_many` calls `reserve(0)` → no growth | no table change; `id=V` still `len=1` |
| 4 | `self.as_mut_ptr()` yields `*mut u8` into `id=V` | **derivation root**: capability for `id=V` resolved and bound to this pointer value |
| 5 | `ptr.add(k)` for k = 0..128 | capability **propagated** through the offset op (not re-resolved) |
| 6 | `ptr::write` at k=1 (first byte past the buffer) | **deref check** vs. propagated cap: `base_v+1 >= base_v + len(1)` → **abort** |

## Findings — both are corrections, not confirmations

### F9 — `case` mode must check *raw* dereferences, not only boundaries

PLAN §3 listed instrumentation points as casts, safe-pointer loads, FFI
boundaries, dealloc re-checks, scope hooks. **Raw-pointer dereference was not
on that list.** Every dangerous write in this CVE is a raw dereference inside
unsafe code. As specified, `case` mode would have inserted *zero* checks on the
overflow path and missed a CVSS-9.8 heap corruption entirely.

This contradicts I1 (total visitation, sparse policy), which was already
correct — §3 had quietly inverted the polarity into an *additive* design
(start from nothing, add checks at seams) when the design must be
**subtractive**: start from checking every access, elide only what the type
system proves. That is also precisely SafeFFI's structure — raw-pointer checks
are *retained*; only safe-pointer checks are hoisted and elided.

**Fix**: §3 gains instrumentation point 0 — every dereference of a raw pointer
is checked; safe-pointer accesses are the ones elided, justified by the cast
check that vetted them.

### F10 — address→allocation lookup is *not* spatial safety; provenance must travel

This is the sharper one. Suppose the deref check were implemented as "look the
faulting address up in the allocation table and verify it's live." At step 6
the overflowing address eventually lands **inside `id=S`, which is live and
valid** — so the lookup succeeds and the check *passes*. The corruption goes
undetected precisely because the victim is another healthy allocation.

Spatial safety requires the capability to come from **where the pointer was
derived**, not from whatever allocation the final address happens to occupy.
Concretely, in `case` mode:

- resolve a capability at *derivation roots* (allocation site, cast site, FFI
  entry, scope entry) — the only places the table is consulted;
- **propagate** it through the MIR dataflow across offset/projection ops
  (`ptr.add`, GEP-equivalents, field projections), narrowing for subobjects
  where known;
- **check at the dereference** against the propagated capability;
- where propagation is lost (int↔ptr round-trips, opaque calls, unions),
  fall back to a table resolve and, if that is ambiguous, apply the v0.5
  per-access validity policy.

Two consequences worth noting:

1. **This is cheaper, not more expensive.** The hot path becomes a register
   compare against a capability already in hand, not a radix lookup. The
   earlier ~2 ns/check probe measured the *lookup* path, which is now the
   cold path at derivation roots only. The overhead hypothesis improves.
2. **`case` and `through` converge earlier than planned.** Propagated
   capabilities are exactly the substrate `through` mode needs (I2); v1 adds
   carrying them across calls and storing them in shadow slots for pointers at
   rest. The staging story gets *stronger*: v0 builds v1's machinery, it just
   doesn't persist it beyond function scope.

### F11 — GWP-ASan sampling does not rescue this

Guard pages catch overflows that run off the end of a *sampled* allocation into
unmapped space. Here the overflow is small, the victim is adjacent and live,
and sampling is probabilistic. Useful defence in depth for opaque C; not a
substitute for provenance checking in instrumented Rust. Keep the framing
honest in the README.

## Integration test spec (`corpus/smallvec-0003`)

- **Fixture**: vendored `smallvec` 1.6.0 (pinned) + the reproducer verbatim.
- **Assert (case)**: aborts at the first out-of-bounds write; report names
  `id=V`'s allocation site and the offending offset; report must **not**
  mention `id=S` as the "owning" allocation (that would indicate an F10
  regression — the canary test for provenance handling).
- **Assert (through)**: identical abort.
- **Assert (control)**: `smallvec` 1.6.1 runs clean under both modes.
- **Regression guard**: a variant with the write landing in *unmapped* space,
  to confirm the test isn't accidentally passing via a segfault.
- Runs as a `nix flake check`, pure/offline.

## Plan deltas produced by this trace

1. §3 gains **instrumentation point 0**: all raw-pointer dereferences checked;
   elision is safe-pointer-only (F9).
2. New invariant **I10**: capabilities are resolved at derivation roots,
   propagated through pointer arithmetic, and checked at the dereference —
   never re-resolved from the faulting address (F10).
3. `cementite`: `check_deref(ptr, size, cap)` becomes the hot-path API;
   `lookup` is demoted to derivation-root/fallback use.
4. Performance note updated: hot path is a register compare, not a lookup.
