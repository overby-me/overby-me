# nix-ninja: per-edge Nix builds from a Ninja graph

Build any Ninja project (hand-written, or generated by CMake / Meson / gn) with
Nix by lowering each Ninja *edge* to its own Nix derivation. A sibling to
`nix/lib/buck2` (per-action Buck2 builds) and `nix/lib/cargo` (per-crate
builds), exposed through the flakelight `perSystemLib` module.

Unlike buck2 (whose build files are Starlark, parsed by `nix/lib/skylark` at
eval time), Ninja's `build.ninja` is a flat, fully-explicit graph — CMake has
already done configuration and codegen resolution. So there is no interpreter:
the reusable `rust/ninja` tool parses the manifest and expands every command,
and a new `-t graph-json` subtool dumps the graph as JSON. nix-ninja reads that
JSON (one IFD) and lowers it.

## Why one IFD (not zero)

buck2 lowers with no IFD because a pure-Nix Starlark interpreter runs at eval
time. For Ninja the parser is `rust/ninja` (compiled Rust), so extracting the
graph is one derivation whose output (JSON) Nix imports. This is deliberate:

- a pure-Nix Ninja parser is feasible (the format is simple), but a real
  `build.ninja` from CMake has tens of thousands of edges; parsing that at eval
  time in Nix would be far slower than a Rust pass emitting JSON.
- the extraction derivation is keyed only on the manifest files, so editing a
  *source* never re-runs it.

## Lowering model

Identical in spirit to `nix/lib/buck2/build/lower.nix`: a virtual build tree
rooted at the Ninja build dir, one derivation per edge, dependencies staged by
symlink (`cp -rs` of a producer's `$out`), sources copied as real files,
commands run against build-dir-relative paths, the tree exported as `$out`.
Phony edges carry no derivation; their aliases are flattened when resolving a
consumer's inputs.

## Header dependencies (the hard part — M3)

A compile edge declares its `.c` as an explicit input, but the headers it needs
are discovered by the compiler at build time via `depfile`/`deps = gcc` — they
are not in the static graph. For per-derivation lowering the inputs must be
known up front. Strategy, in order of preference:

1. **Include-dir staging (planned default).** Parse `-I<dir>`/`-isystem` from
   the edge's expanded command and stage those directories (content-addressed)
   as inputs, alongside the explicit `.c`. Editing a source rebuilds only its
   edge; editing a header rebuilds the compiles whose `-I` covers it. Correct,
   and incremental for the common (source-edit) case.
2. **Depfile precision (later).** Do one reference build to capture `.d`
   depfiles, then use the exact header set as explicit inputs. Finest
   granularity; needs a bootstrap build.
3. **Whole-tree staging (fallback).** Stage the entire source tree per compile.
   Always correct, poor incrementality (any source edit touches every compile).

## Milestones

- [x] **M1 — graph extraction.** `rust/ninja` `-t graph-json`: dump every edge
  with fully-expanded command, all in/out/dep paths, depfile, rspfile, deps
  mode, restat/generator/pool.
- [x] **M2 — lower + trivial build.** `build/lower.nix` + `buildNinjaProject`;
  the hand-written `trivial` fixture builds one derivation per edge and runs
  (`ninja-build-trivial` check).
- [x] **M3 — real CMake + per-file incrementality.** CMake configured in a
  derivation (source in the store), graph extracted, each edge lowered. CMake's
  absolute source refs are rewritten to build-dir-relative and staged
  content-addressed *per file*, so editing one `.c` rebuilds only its object
  (proven: editing `main.c` leaves `greet.c.o` cached). Generated headers in the
  build dir resolve via a content-addressed copy of the configured dir (stable
  across source edits). Static libraries (`ar`/`cmake -E`) and multiple targets
  work. Checks: `ninja-build-{trivial,cmake,cmake-lib}`.
- [x] **M4 — scale to Darling (launcher builds).** Darling's **38,362-edge**
  tree configures through `buildNinjaProject` (`configureNativeBuildInputs`/
  `configureBuildInputs`: clang, python, bison, flex, pkg-config, libcap, and
  the project's lib deps); `graph-json <target>` target-filters the `darling`
  launcher to a **3-edge** subtree; the edges lower, `darling.c` compiles with
  clang, and the link produces a real `ELF 64-bit LSB pie executable`. The
  `_ninja-darling-launcher` check (impure) builds it in per-file
  depfile-precise mode (M5): the compile scan discovers `darling.c`'s
  source-relative `#include "../shellspawn/shellspawn.h"` and stages it, so the
  launcher keeps per-file incrementality with no whole-tree mount.

  Per-edit cost today: one CMake reconfigure (~30s for Darling; the graph and
  all unchanged compiles stay cached) + the changed target's compile+link.
  A large win over the ~45-minute full build, though not seconds-level — see
  configure-stability below.
- [x] **M5 — depfile-precise staging.** For each compile edge (identified by a
  gcc/msvc `deps` mode, a non-empty `depfile`, and a source-file input; the
  last excludes CMake link edges, which also carry `deps = gcc` + a `link.d`),
  run a preprocess-only `-M` scan (`build/lower.nix` `scanDepsOf`) with the
  rewrite roots mounted, parse the emitted depfile (`parseDepfile`) for the
  exact set of headers read (including source-relative `#include "../x.h"` that
  no `-I` covers), and stage precisely those files, dropping the coarse
  `-I`-dir staging. Keeps per-file incrementality correct for multi-target
  builds and for the Darling launcher. The scan command drops output/`-c`/`-M*`
  flags and appends `-M -MF "$DEPS_OUT"`. Checks: `ninja-build-{cmake,cmake-lib}`
  and `_ninja-darling-launcher` (real source-relative include).

  Follow-ups (not blocking):
  - **Configure-stability** (deferred, analyzed). buck2's `ifdAnalysis` keys
    analysis on build files only by building a placeholder source (real build
    files, emptied sources). Two obstacles here: (a) CMake `file(GLOB)` targets
    (Darling has them) get "No SOURCES" if sources are *excluded*, so the
    placeholder must keep files present but *emptied* — a CA derivation
    (`__contentAddressed`, available here) that copies + truncates; (b) that
    copy of a 4 GB source per edit costs about as much as the reconfigure it
    saves. So for a huge tree it is not a clear win; nix-ninja's real payoff
    there is per-edge **caching** (hermetic, shared via Cachix, distributable),
    not local latency — for pure local iteration `nix develop` + `ninja` over a
    persistent build dir is faster. Worthwhile for smaller expensive-to-
    configure projects.
  - **rspfile** coverage for long link commands (present, untested at scale);
    **codegen edges** (`mig`/`wrapgen`, 3,467 `CUSTOM_COMMAND`) exercised by
    larger targets.
  - Production integration reuses `nix/package.nix`'s exact configure inputs
    (in the darling-nix repo, via an overby.me flake input) instead of the
    hand-listed deps in the check.

## Files

- `default.nix` flakelight module: `buildNinjaProject` and `ninjaLib` via
  `perSystemLib`.
- `build/buildNinjaProject.nix` entry point: graph extraction (IFD) + build.
- `build/lower.nix` the per-edge lowering.
- `tests/fixtures/` Ninja fixtures; `checks.nix` flake checks.
- `rust/ninja/src/tools/graph_json.rs` the `-t graph-json` dumper.
